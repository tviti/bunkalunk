## On the app/command structure

The instinct here is right. `lunk show <segment>` already feels like it's doing two different things — it's a query interface *and* a presentation layer — and once you add ride-level stats, power analysis, or anything else, you'll be stacking subcommands onto a single CLI that has no coherent identity.

The "unitary app" framing is a good one. The idea would be:

- **`bunk`** is the cache manager. One job: get data in, keep the cache healthy.
- **`lunk`** is the analysis plumbing. One job: run computations (segment matching, derived stats, etc.) and write results to SQLite. It doesn't own presentation.
- **Apps** are thin, purpose-built CLI tools that read from SQLite and present results. `leaderboard`, `ride-summary`, etc.

This keeps `lunk` stable and narrow — it's the engine. Apps are cheap to add, cheap to change, and don't destabilize the core. If a leaderboard format changes or you want a new view, you don't touch `lunk`.

The question is where apps live. A few options:

1. **Scripts in `bin/` or `tools/`** — dead simple, low ceremony, each one is just a small Python script that queries SQLite and formats output. Easy to add.
2. **A thin `apps/` package** — same idea but with a bit more structure if they grow.
3. **Named entry points in `pyproject.toml`** — `leaderboard`, `ride-summary` etc. become real commands without needing to live in the same source hierarchy.

Option 1 or 3 is probably right for now. The spec doesn't need to mandate much here — just establish the principle that apps are consumers of SQLite, not owners of analysis logic, and that `lunk` is the thing that produces the data they read.

---

## On the Python/Julia SQLite boundary

This is the more structurally important one. Right now the spec implies that Julia writes segment efforts to SQLite and Python owns the schema. That's two writers with no defined coordination mechanism — which is fine until the schema changes, and then it's a maintenance headache.

A few ways to think about this:

**Option A: Python owns all SQLite writes, Julia is read-only**

Julia computes results and returns them to a Python caller, which writes to SQLite. Clean boundary: one writer, one schema owner. The cost is that you need a Python/Julia interop layer (subprocess call, shared data format like JSON/msgpack over stdout, or something like `PyJulia`). Subprocess with structured output (JSON lines or similar) is the most boring and probably most robust option.

**Option B: Julia owns its own writes, shares the schema definition**

You maintain the schema in one place (a SQL file or Python schema module) and Julia reads that canonical definition. Julia gets its own connection and writes its own tables. The risk is drift — if Python migrates the schema, Julia has to be updated in sync.

**Option C: Julia never touches SQLite directly — all persistence goes through `lunk` as a plumbing layer**

Julia computes, emits structured results, `lunk` (Python) handles all reads and writes. `lunk` becomes the single SQLite gatekeeper. This is essentially Option A but with the boundary made explicit in the architecture: Julia is a pure computation engine, Python handles all I/O with the operational database.

**My inclination is Option C.** It's the most boring, it eliminates the two-entrypoint problem entirely, and it maps cleanly onto the existing split: Python does I/O and orchestration, Julia does computation. The spec already gestures at this but doesn't make it explicit enough. Making it a stated design principle — *Julia emits results, Python persists them* — closes the ambiguity.

The one thing to nail down then is the interchange format between Julia and Python. Newline-delimited JSON over stdout is boring and it works. You could also consider a temporary SQLite write by Julia into a scratch table or file that Python then reads and commits — but that's more moving parts than you need.

> Re-decoding a source path replaces that path’s prior decoded activity record and updates `decoded_ref`. Derived analysis rows associated with the prior decoded activity must be recomputed or invalidated before reuse.

- Provide a parse method to read the source file

** HDF5 Cache Architecture: From Monolith to CAS
   [2026-04-12 Sun]

   The decision was made to shift the HDF5 cache from a single monolithic file to a Content Addressable Storage (CAS) mirror.

   *** The Problem with the Monolith
   - Blast Radius: Single point of failure. Corruption of the file header destroys the entire cache.
   - Concurrency: HDF5 locking makes simultaneous read/write (e.g., analysis while ingesting) difficult without SWMR complexity.
   - Evolution: Updating the schema for some activities requires rewriting the entire monolithic file.

   *** The CAS Solution
   - Structure: Each ride is stored as a separate HDF5 file, named by its SHA-256 content fingerprint (e.g., /cache/abc123...h5).
   - Index as Bridge: SQLite continues to act as the operational index, mapping human-readable source paths to these fingerprints.
   - Loader Abstraction: A dedicated loader subroutine abstracts this lookup, allowing analysis tools to request rides by path while the system retrieves them by hash.

   *** Strategic Value
   - Resilience: Corruption is localized to a single ride.
   - Concurrency: Asynchronous access is native; adding new rides doesn't block reads of existing ones.
   - P2P Foundation: This architecture is a prerequisite for a P2P sharing network, where rides are identified and exchanged via hashes rather than paths.
   - Ecosystem: Decoupling the data (CAS) from the provenance (Index) allows other tools (R, Jupyter) to consume the cache without needing the full ingestion logic.

** HDF5 Storage Sharding
[2026-04-12 Sun]

#+begin_src markdown
### Avoiding Directory Proliferation
While a single directory for all HDF5 files is sufficient for most users, it can lead to OS-level performance degradation (slow listing, inode exhaustion) at extreme scales (10k+ files).

The decision is to bake in **Directory Sharding** from the start to avoid future migrations.

### Implementation
The CAS will use a prefix of the SHA-256 fingerprint to create subdirectories.
Example: a fingerprint `af1234...` is stored at `/activity_store/af/1234...h5`.

Using the first 2 characters of the hex hash provides 256 subdirectories, distributing the load and ensuring filesystem performance regardless of the total activity count.
